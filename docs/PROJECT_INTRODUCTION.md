# 3D 异构 CIM 资源调度优化系统

## 1. 项目概览

**项目名称**：面向 MoE 大模型推理的 3D 异构 CIM 资源调度优化

**参赛信息**：2026 INNO CIM 存算一体高校挑战赛，赛道二 / 赛题二

**队名**：没头绪

**成员**：祝铭堃，南开大学

**项目类型**：面向 MoE 专家权重部署与静态调度的编译工具链原型

本项目针对 3D 异构存算一体资源上的 MoE 专家权重部署问题，建立从模型描述和 Expert 激活轨迹输入，到 Weight-Cube 切分、共现感知映射、副本放置、静态调度、性能模拟和提交文件生成的完整流程。系统重点解决资源容量有限、同一 Sub-Cube 内的互斥执行、跨 Sub-Cube 依赖传输以及热点 Expert 访问不均衡等问题。

项目不是一个完整的大模型推理框架，也不声称完成真实芯片上的端到端 DeepSeek 推理。当前实现的评价对象是赛题二要求的 MoE Expert 权重部署、资源映射和静态调度过程；Attention 和 KV Cache 不在本项目的核心范围内。

## 2. 一页讲清：方法与创新

### 方法主线

本项目的核心方法可以概括为：**轨迹统计驱动的 3D Weight-Cube 映射，加上面向 Sub-Cube 约束的静态调度与独立验证**。

给定模型算子、专家权重尺寸和 Expert 激活轨迹，系统先把大权重拆成可放置的 Weight-Cube，再从轨迹中计算 Expert 频率、共现和转移关系。映射阶段用这些统计结果构建互斥分组，识别热点 Expert，并在有限物理容量预算下选择副本位置；调度阶段再将映射结果转换为满足依赖、互斥、切换和传输代价的静态任务序列。最后，独立验证器检查生成结果是否真的满足空间和时间约束。

### 方法创新点

1. **从“只看权重大小”升级为“激活轨迹感知映射”**：把 Expert 的频率、共现和转移关系显式引入资源放置，使映射目标与真实 MoE 访问模式相关，而不是只执行无差别的 First Fit。
2. **把 3D 空间放置和时间调度联合考虑**：同时处理 `N x N` Sub-Cube 空间、`D x H x W` 三维容量、同一 Sub-Cube 互斥、跨 Sub-Cube 传输和 DAG barrier，避免空间合法但执行不可行的结果。
3. **用有限副本预算缓解热点冲突**：副本不是无限复制，而是在容量上限内优先服务高频 Expert，并通过多样性、容量峰值和转移代价控制副本收益与资源消耗的平衡。
4. **建立“优化器之外”的可验证闭环**：映射器输出不是最终可信度来源，独立验证器重新检查边界、重叠、容量、互斥、依赖和映射率，使结果可以作为提交产物和答辩证据。
5. **保留可解释中间表示和轨迹适配边界**：通过 `internal_ir.json`、`run_manifest.json` 和规范化轨迹接口保存决策上下文，官方轨迹到达后可以替换输入并重新验证，而不需要重写算法主干。

### 与简单基线的差异

| 方法 | 主要依据 | 是否使用轨迹结构 | 是否处理时间约束 | 是否有独立验证 |
| --- | --- | --- | --- | --- |
| First Fit | 权重尺寸和空闲空间 | 否 | 弱 | 可选 |
| 仅 Best-Fit | 空间碎片和局部容量 | 否 | 弱 | 可选 |
| 本项目 | 频率、共现、转移、空间和调度反馈 | 是 | 是 | 是 |

因此，答辩时应先讲清“为什么这样映射”和“为什么这样调度”，再展示代码结构和实验数字。

## 3. 问题背景

传统大模型推理通常将权重存储和计算资源分离，数据移动会产生明显的带宽和延迟成本。CIM 架构将部分计算能力放入存储阵列附近，可以减少权重搬运，但也引入了新的资源管理问题：

1. 3D CIM 空间具有 Sub-Cube、层深和二维平面位置等多级资源约束。
2. 一个 Weight-Cube 可能占据多个连续深度层，并且不同 Weight-Cube 不能在空间上重叠。
3. 同一 Sub-Cube 在同一时刻只能激活一个 Weight-Cube，不同 Sub-Cube 可以并行。
4. MoE Expert 的激活具有频率、共现和转移结构，简单的 First Fit 容易造成热点拥塞和切换开销。
5. 上游任务的多个 Section 完成后，下游任务才能继续执行，需要显式建模依赖屏障。

本项目将上述问题统一为“空间映射 + 静态调度 + 约束验证”的优化流程，使生成的映射和调度结果可以被独立检查和复现。

## 4. 核心方案

### 3.1 端到端流程

系统流程如下：

```text
模型 JSON / ONNX 元数据
        +
激活轨迹 JSON
        |
        v
模型解析与 Weight-Cube 切分
        |
        v
共现统计、互斥分组、热点分析
        |
        v
Best-Fit 映射 + 热点子图分配 + Expert 副本放置
        |
        v
静态依赖调度与性能模拟
        |
        v
solution.json / mapping / schedule / metrics
        |
        v
严格提交验证器
```

### 3.2 模型解析与轨迹适配

`src/model_parser.py` 将输入转换为统一的 `ParsedModel`。输入可以是项目使用的 JSON 模型描述，也可以是带有 ONNX 风格算子元数据的描述。解析阶段保留算子类型、输入输出关系、初始化权重信息和模型 DAG。

激活轨迹适配器支持以下顶层封装：

- `traces`
- `records`
- `activations`

单条轨迹记录兼容以下专家字段：

- `active_experts`
- `expert_ids`
- `experts`
- `topk_experts`

因此，官方轨迹文件到达后可以替换输入文件并复用后续流程。当前公开材料中的 `trace_balanced`、`trace_base`、`trace_hotspot` 和 `trace_bursty` 是自定义测试轨迹，不应被描述为官方轨迹。

### 3.3 3D CIM 资源模型

资源空间使用 `N x N` 个 Sub-Cube 构成全局二维阵列，每个 Sub-Cube 具有 `D x H x W` 的三维容量。Weight-Cube 通过起始坐标、尺寸和所属 Sub-Cube 放置到资源空间中。

主要约束包括：

- 位置坐标必须落在全局资源边界内。
- 同一 Sub-Cube 内的 Weight-Cube 不能发生体积重叠。
- 同一 Sub-Cube 同一时刻只能运行一个任务。
- 依赖任务必须满足严格的先后关系和 barrier 约束。
- 映射率必须达到 1.0，不能存在未放置的逻辑 Weight-Cube。
- 严格容量模式下，逻辑模型体积与物理资源体积的比值不能超过配置上限。

### 3.4 共现感知映射

系统从激活轨迹中提取专家频率、共现关系和相邻转移关系。共现频率高的专家更容易在同一推理请求中同时出现，因此不适合无条件放入同一个互斥资源组。映射器执行以下步骤：

1. 根据专家共现关系进行多起点互斥分组。
2. 根据激活频率识别热点 Expert 和热点子图。
3. 使用 Best-Fit 和面积/深度约束完成基础 Weight-Cube 放置。
4. 对热点 Expert 进行有限预算的副本放置，降低排队和切换压力。
5. 使用局部搜索和可选模拟退火改善冲突、负载和转移代价。
6. 对容量、边界、重叠和副本预算进行检查。

副本是调度层面的空间换时间策略，不代表训练阶段的权重更新或真实芯片上的物理复制电路。正式 V5 结果关闭了 shared/non-expert operator replication，额外预算主要服务于 MoE Expert 副本。

### 3.5 静态调度与性能模拟

`src/simulator.py` 根据模型 DAG、Weight-Cube 映射和硬件配置生成静态调度。模拟器包含：

- 计算周期模型。
- Z 轴深度访问惩罚。
- Weight-Cube 切换惩罚。
- 跨 Sub-Cube 依赖传输惩罚参数。
- 带宽和传输/计算重叠模型。
- 同一 Sub-Cube 的资源互斥。
- 上游多任务汇聚后的依赖屏障。

跨 Sub-Cube 互连延迟不是题目固定值，当前默认参数为 0。若设置非零值，模拟器会在跨 Sub-Cube 依赖边上加入传输惩罚。正式报告中应将该参数称为建模假设或敏感性参数，而不是芯片实测值。

### 3.6 提交验证器

`scripts/validate_submission.py` 对输出目录执行独立检查，覆盖：

- `solution.json` 必需字段。
- Weight-Cube 坐标和尺寸边界。
- 物理放置重叠。
- 同一 Sub-Cube 的时间互斥。
- 跨任务依赖和并行关系。
- 未放置 Weight-Cube。
- `mapping_rate`。
- 严格容量比例。

验证器的输出保存在 `validation_report.json`，其中 `ok=true` 且 `errors=[]` 才可作为提交候选。

## 6. 当前正式结果

正式提交推荐使用 `outputs/submission_v5_primary`，而不是将更低延迟但尚未经过官方轨迹验证的候选结果直接宣传为最终结果。

| 方案 | 延迟（cycles） | 延迟降低 | 空间利用率 | 冲突分数 | 状态 |
| --- | ---: | ---: | ---: | ---: | --- |
| First Fit 基线 | 539,729 | 0.00% | 0.5035 | 6.0 | 基线 |
| V5 primary | 234,436 | 56.56% | 0.5868 | 2.0 | 正式推荐 |
| V5.1 | 231,672 | 57.08% | 0.6701 | 4.0 | 候选 |

V5 primary 的严格容量比例为 `1.9862`，`mapping_rate=1.0`，验证器结果为 `ok=true`。这些数字来自项目的 `trace_balanced` 模拟轨迹，属于模拟器结果，不是实测芯片延迟。

另有 128 Expert 的 metadata-only 大规模证明：优化延迟 64,863 cycles、延迟降低 63.09%、容量比例 1.9427、验证器通过。该结果用于说明工程流程可扩展，不代表真实 DeepSeek-671B 权重已完整部署。

## 7. 项目创新点

1. **激活轨迹驱动的映射**：不只按权重体积放置，还使用频率、共现和转移统计指导互斥分组和热点副本。
2. **空间与时间联合约束**：同时检查 3D 物理放置、Sub-Cube 互斥、依赖屏障和跨 Sub-Cube 传输。
3. **可复现的中间产物**：保留 mapping、simulation、`solution.json`、`run_manifest.json`、`internal_ir.json` 和验证报告，便于复核。
4. **严格提交验证**：把容量、边界、重叠、依赖和映射率检查从优化器中独立出来，避免只报告目标函数而不验证结果可提交性。
5. **面向官方轨迹的适配接口**：轨迹解析器允许替换不同 JSON 外壳和字段命名，降低官方文件到达后的接入成本。

## 8. 已知边界

- 当前公开结果使用自定义轨迹，官方 `activation_trace.json` 到达后需要重新运行并更新结果。
- 当前性能结果来自离散事件/周期级抽象模拟，不是具体 CIM 芯片 RTL 或硅后测量。
- Attention、KV Cache、真实通信网络协议和完整大模型数值推理不在赛题二实现重点内。
- `switching_penalty`、`z_access_penalty` 和跨 Sub-Cube 传输参数需要在最终报告中继续补充论文依据和敏感性分析。
