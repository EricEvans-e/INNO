\section{系统结构与接口设计}
图~\ref{fig:architecture} 展示了系统的数据流。解析器输出算子、依赖 DAG 与 Weight-Cube；轨迹模块输出共现、频率、burstiness 和转移影响；映射器生成物理放置及副本元数据；模拟器生成静态 schedule 和性能指标；验证器最终检查空间边界、重叠、调度互斥、依赖与映射率。各阶段均以 JSON 产物固化，因而能够从最终 \texttt{solution.json} 回溯到输入哈希和配置。

输入模型采用算子级元数据表示，支持线性、MoE 专家、MatMul/Gemm 与轻量非线性任务。ONNX 路径是 initializer-backed 结构适配，不宣称覆盖完整 ONNX 执行语义。激活轨迹适配器接受顶层 \texttt{traces}、\texttt{records} 或 \texttt{activations} 等格式，并统一单条记录的专家字段，例如 \texttt{active\_experts}，为后续替换官方轨迹保留接口。

\subsection{中间产物与接口契约}
系统以文件接口隔离解析、优化和评估三个阶段。解析阶段至少产生算子列表、依赖边、Weight-Cube 列表和轨迹统计；映射阶段产生逻辑到物理副本的对应关系、复制预算和容量摘要；调度阶段产生任务 ID、物理位置、开始周期、持续时间和前驱信息；最终由验证器读取这些产物，而不是调用模拟器内部对象。这样做有两个直接作用：一是便于替换官方轨迹而不重写优化器，二是允许评委只检查结构化结果而不依赖本地运行时状态。

\texttt{solution.json} 是提交级接口，核心字段为硬件配置、\texttt{weight\_cubes} 和 \texttt{schedule}。

表~\ref{tab:interfaces} 汇总了主要接口的最小字段。字段设计遵循“生成阶段写入、后续阶段只读”的原则：映射器不改写模型依赖，模拟器不补造缺失放置，验证器只根据保存的结构化结果进行检查。该约束降低了调试时把内存状态误认为提交证据的风险。

当输入轨迹采用不同封装时，适配器先将顶层 \path{traces}、\path{records} 或 \path{activations} 转成统一记录，再从 \path{active_experts}、\path{expert_ids}、\path{experts} 或 \path{topk_experts} 中读取激活专家。若记录缺少可解释的专家字段，系统应在解析阶段报错，而不是静默生成空统计。这个接口约束是后续接入官方轨迹时的最低兼容条件。

运行清单 \path{run_manifest.json} 保存模型与轨迹哈希、命令行参数、随机性开关、版本摘要和输出文件关系。内部 IR 文件 \path{internal_ir.json} 使用项目自定义的 \path{cim_3d_scheduler.ir.v1} schema，面向审阅和交接，不冒充 MLIR 或硬件 ISA。验证器的输出固定为 \texttt{ok}、\texttt{errors}、\texttt{warnings} 和指标摘要，形成“生成—保存—独立复核”的闭环。
